# Compiling to CWL

Everything you have run in this guide went through one translation: Sophios
compiled your workflow into CWL and handed that to a runner. This chapter
opens the base path after a compile, `autogenerated/` under the current
directory unless you moved it with `--basepath`, or `basepath=` in Python,
and reads every file in it, so that you know
why each line is there. It reads the output of the
[first workflow](first-workflow.md), explains the names, and covers the two
ways to package the result and how to run it on a CWL runner of your own.

CWL is the one backend Sophios has today, and it writes CWL v1.2: one
`Workflow` document, one `CommandLineTool` document per step, and a job
file. Everything on this page is about what that backend writes;
[The workflow model](workflow-model.md) is what it writes from.

To produce the files without running anything, compile alone, in either
form:

```bash
sophios --yaml greeting.wic --generate_cwl_workflow
```

```python
from greeting import workflow

compiled = workflow().compile()
compiled.write_cwl('autogenerated')
compiled.write_job_inputs('autogenerated')
```

The command line writes the tree below. `write_cwl()` writes the workflow
with every tool embedded in it, as one file, and `write_job_inputs()` the
job file beside it.

## The tree

```text
autogenerated/
  greeting.cwl
  greeting_inputs.yml
  greeting.names.json
  greeting__step__1__touch/touch.cwl
  greeting__step__2__append/append.cwl
  greeting__step__3__cat/cat.cwl
```

Each step gets a directory named for it, holding its tool. A subworkflow's
directory holds its own `.cwl`, its own job file and its own step
directories, so the tree nests as the workflow does. Beside each tool is a
`<tool>_inputs.yml`, which is empty: a step's values are the workflow's
inputs, and nothing is bound to the tool itself.

## The workflow

```yaml
#!/usr/bin/env cwl-runner
# This file was autogenerated using Sophios, version <version>
# https://github.com/PolusAI/sophios
steps:
- id: greeting__step__1__touch
  in:
    filename:
      source: greeting__step__1__touch___filename
  run: greeting__step__1__touch/touch.cwl
  out:
  - file
- id: greeting__step__2__append
  in:
    str:
      source: greeting__step__2__append___str
    file:
      source: greeting__step__1__touch/file
  run: greeting__step__2__append/append.cwl
  out:
  - file
- id: greeting__step__3__cat
  in:
    file:
      source: greeting__step__2__append/file
  run: greeting__step__3__cat/cat.cwl
  out:
  - output
cwlVersion: v1.2
class: Workflow
$namespaces:
  edam: https://edamontology.org/
  sophios: https://github.com/PolusAI/sophios#
$schemas:
- https://raw.githubusercontent.com/edamontology/edamontology/master/EDAM_dev.owl
inputs:
  greeting__step__1__touch___filename:
    type: string
  greeting__step__2__append___str:
    type: string
sophios:lang_version: 0.0.1
outputs:
  greeting__step__1__touch___file:
    type: File
    outputSource: greeting__step__1__touch/file
  greeting__step__2__append___file:
    type: File
    outputSource: greeting__step__2__append/file
  greeting__step__3__cat___output:
    type: string
    outputSource: greeting__step__3__cat/output
```

Read it top to bottom, and each part answers one question:

- `steps:` lists the three steps, renamed, and for each one where every
  input comes from (`in:`), which tool file it runs (`run:`), and which
  outputs later steps or the workflow may use (`out:`). `source:` is an
  edge: `greeting__step__1__touch/file` is the output `file` of the first
  step.
- `cwlVersion`, `class`, `$namespaces` and `$schemas` make it a standalone
  CWL v1.2 document that a runner can load without Sophios.
- `inputs:` holds the two values you wrote, `greeting.txt` and
  `Hello, Sophios`, as inputs of the workflow; their values are in the job
  file, below.
- `sophios:lang_version` records which version of the `.wic` language the
  document was read as.
- `outputs:` exposes every step's outputs, so a run keeps all of them.

Nothing in it is specific to Sophios except the `sophios:` line, which a
runner ignores. The rest of this chapter explains why the names look as
they do, where your values went, and what the compiler adds for the
constructs of the later chapters.

### Step names

Each step is `<workflow>__step__<n>__<id>`: the workflow's name, the step's
1-based position, and its id. The position makes the name unique when a tool
appears twice, and the id keeps it readable. Inside a subworkflow the parts
are joined with `___`, so a step two levels down reads
`nested__step__1__make_greeting.wic___make_greeting__step__1__touch`. The
spelling is one-way: Sophios never takes a name apart, and a program that
needs to know what a name came from reads `<workflow>.names.json`, which maps
every step id to its workflow, position, name, file and line, and every
derived port name to its step and port.

A process that is not found by stem on a search path is registered under its
stem plus a hash of where it came from: a tool or workflow named by a `run:`
path (`child_dca52324`, hashed from the path relative to the root document),
or an inline `run:` body (hashed from the body). That registry name is the
name a called workflow carries in the compiled tree, so the steps inside a
`run: child.wic` call read `<call>___child_dca52324__step__1__touch`, and the
ports they expose are derived from it. Choosing an implementation of a
dispatcher workflow hashes nothing: `- id: disp.wic`, found on a search path,
compiles to `disp.cwl` and `disp__step__1__touch` whichever implementation is
chosen, while `run: wf/disp.wic` compiles to `disp_0c297e37.cwl` because it
is a path. Two files with one stem are two names, and the hash is stable as
long as the file does not move. A step id is never hashed: the step is still
named for what you wrote.

### Inputs and the job file

A literal is not written into the CWL. Each becomes a workflow input named
`<step>___<port>`, and its value goes in the job file:

```yaml
greeting__step__1__touch___filename: greeting.txt
greeting__step__2__append___str: Hello, Sophios
```

So the CWL is the same whatever values you gave, and a different job file
runs the same workflow on different data. A workflow input you declared keeps
its name; an input inference could not fill is added under its derived name
with no value. Before a run, every relative `File` or `Directory` path in the
job is written absolute, so the runner finds it wherever it reads the job
from.


### Edges and outputs

An edge is `<step>/<port>`. A connection you wrote is under `source:`, as
in `greeting.cwl` above; an inferred one is written bare, as
`file: greeting_inferred__step__1__touch/file`. Both mean the same to a
runner.

Every step output is exposed as a workflow output under its derived name, and
a named output is added under yours. `Workflow.compile()` of a Python
workflow that names outputs returns only those; `Workflow.run()`, like the
command line, keeps both. The [greeting_output pair](connecting-steps.md)
begins:

```yaml
outputs:
  greeting:
    type: File
    outputSource: greeting_output__step__2__append/file
  greeting_output__step__1__touch___file:        # the command line and run(); not compile()
    type: File
    outputSource: greeting_output__step__1__touch/file
  greeting_output__step__2__append___file:
    type: File
    outputSource: greeting_output__step__2__append/file
```

### Scatter and conditions

A scattered step carries `scatter` and `scatterMethod` as written, its
outputs are typed as arrays, and `ScatterFeatureRequirement` is added. The
[greet_many pair](scatter-and-conditions.md):

```yaml
requirements:
  ScatterFeatureRequirement: {}
steps:
- id: greet_many__step__2__append
  scatter:
  - file
  - str
  scatterMethod: dotproduct
outputs:
  greet_many__step__3__cat___output:
    type:
      type: array
      items: string
    outputSource: greet_many__step__3__cat/output
```

A conditional step carries `when` as written, and `InlineJavascriptRequirement`
is added. The [greeting_if pair](scatter-and-conditions.md), whose record
binds the workflow input `show` to an input the tool does not declare:

```yaml
requirements:
  InlineJavascriptRequirement: {}
inputs:
  show:
    type: boolean
steps:
- id: greeting_if__step__3__cat
  in:
    file:
      source: greeting_if__step__2__append/file
    show:
      source: show
  when: $(inputs.show)
```

### Records

A record is written as CWL's `WorkflowStepInput`, its sources resolved, and
the requirements it needs added: `MultipleInputFeatureRequirement` for
several sources or a `linkMerge`, `StepInputExpressionRequirement` for a
`valueFrom`, `InlineJavascriptRequirement` for an expression `valueFrom`. The
[record pair](types-and-records.md):

```yaml
requirements:
  MultipleInputFeatureRequirement: {}
steps:
- id: record__step__3__concat
  in:
    files:
      source:
      - record__step__1__touch/file
      - record__step__2__echo/stdout
      linkMerge: merge_flattened
```

### Subworkflows

A subworkflow call is a step whose `run:` is the child's own `.cwl`, compiled
to a directory named for the calling step with its tools beside it, and
`SubworkflowFeatureRequirement` is added. The [nested pair](subworkflows.md):

```yaml
requirements:
  SubworkflowFeatureRequirement: {}
steps:
- id: nested__step__1__make_greeting.wic
  run: nested__step__1__make_greeting.wic/make_greeting.cwl
  out:
  - greeting
  - make_greeting__step__1__touch___file
  - make_greeting__step__2__append___file
- id: nested__step__2__cat
  in:
    file:
      source: nested__step__1__make_greeting.wic/greeting
```

The child exposes its named output and every inner step output, and the
parent exposes them again under names joined with `___`.

### What the compiler adds

- `cwlVersion: v1.2` and `class: Workflow`, whatever the document said; a
  `cwlVersion` other than `v1.0`, `v1.1` or `v1.2` is `wic035`.
- `$namespaces` with `edam` and `sophios`, and `$schemas` with the EDAM
  ontology. Prefixes you declared survive, except those two; a prefix a
  promoted port's `format` uses is declared as the tool binds it, and two
  tools that bind one prefix to different URIs for promoted ports are
  `wic031`.
- `sophios:lang_version`, the language version the document was read under.
- The requirements the steps need, each only when you did not write it:
  `ScatterFeatureRequirement` for a scatter, `SubworkflowFeatureRequirement`
  for a subworkflow step, `InlineJavascriptRequirement` for a `when` or an
  expression `valueFrom`, `MultipleInputFeatureRequirement` for a record with
  several sources or a `linkMerge`, `StepInputExpressionRequirement` for a
  `valueFrom`.

Everything else you wrote at the top level of a `.wic` document or on a step
(`doc`, `label`, `hints`, a `requirements:` body) is copied through as it is;
`inputs` and `outputs` are merged into, the compiler winning on a name
collision. The [language specification](dev/language_spec.md) lists what
happens to each CWL field.

## The tools

Each tool is copied beside the workflow in a canonical form: `inputs` and
`outputs` as mappings keyed by name, whatever form the source used; a
`stdout`/`stderr` of `<stem>.out`/`<stem>.err` added under `--quiet` when the
tool names none. Its `cwlVersion` stays what the file said (`touch.cwl` stays
`v1.0`), since each tool is its own document. A tool given inline under
`run:` is written at `v1.2`. On the command line, a `dockerFile` given by
`$include` has its path made absolute, so the runner finds the Dockerfile from
wherever it runs.

## Packaging options

Two flags change how the tree is packaged, and neither changes what the
workflow does.

`--cwl_inline_subworkflows` writes one flat workflow: each subworkflow call
that carries nothing but `in` and `out`, whose child is not marked
`wic: inlineable: false`, is replaced by the child's steps, renamed
`<call>___<inner step>`; the tools stay separate files. A call that stays
nested is named on stderr with the reason. The root's inputs, outputs and job
file are unchanged.

`--cwl_inline_runtag` writes one self-contained file: every `run:` carries
its process, tools and subworkflows alike, and the shape is unchanged. An
embedded process has no `cwlVersion` of its own, so a v1.0 tool embedded in
the v1.2 workflow would lose the defaults v1.0 gave it; Sophios adds those two
as hints (`NetworkAccess: true`, `LoadListingRequirement: deep_listing`), as
cwltool's own upgrader does, so the tool behaves as it did as a file.
`Workflow.compile()` returns the workflow in this form, with every `run:`
embedded, which is why `compiled.cwl_workflow` is one document.

Together the two give one flat, self-contained file.

## Running the result elsewhere

The output is standard CWL. To run it with a runner of your own, give it the
workflow and the job file:

```bash
cwltool autogenerated/greeting.cwl autogenerated/greeting_inputs.yml
```

Leave out the job file and cwltool cannot start, because the workflow's
inputs have no values. It says so by printing the inputs the workflow takes,
which are the values you wrote, under their generated names:

```text
...
usage: autogenerated/greeting.cwl [-h] --greeting__step__1__touch___filename
                                  GREETING__STEP__1__TOUCH___FILENAME
                                  --greeting__step__2__append___str
                                  GREETING__STEP__2__APPEND___STR
                                  [job_order]
```

Two things to know. A Sophios run writes the job file's relative `File` paths
absolute; a compile-only run leaves them as written, and a CWL runner then
reads them relative to the job file, in `autogenerated/`. And a tool that uses
`cwltool:CUDARequirement` needs cwltool's `--enable-ext`. `--generate_run_script` writes the exact command
Sophios would run, flags included, and `--allow_raw_cwl` lets Sophios itself
run a CWL workflow it did not compile, with its pre-flight and image pulls
([Steps and tools](steps-and-tools.md)).

## Why these choices

- **Literals in the job file** keep the CWL free of data, so a workflow is
  reviewable and reusable as a document and its inputs as another.
- **Derived names** carry the structure (workflow, position, name) in a
  spelling the CWL schema allows, since CWL has no place for arbitrary extra
  tags on a step. The names map exists because that spelling is not meant to
  be read back.
- **Every output exposed** means a run keeps everything; a named output is a
  stable handle on top, not a filter.
- **Relative `run:` paths** keep a subworkflow's tree independent of the
  parent that embeds it, so the same child compiles the same wherever it is
  called from.

## Recap

The CWL backend writes the workflow, a tool per step and a job file into the
base path. Steps are renamed `<workflow>__step__<n>__<id>`, every value you
wrote becomes a workflow input with its value in the job file, every step
output is kept as a workflow output, and the requirements the steps need are
added. The result is plain CWL that any CWL runner can run without Sophios.
